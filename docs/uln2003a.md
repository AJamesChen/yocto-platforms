# ULN2003A stepper motor

The image includes a device-tree-bound kernel driver and `uln2003a-test`.
The driver generates an eight-phase half-step sequence for a four-coil unipolar
motor through a ULN2003A module. The default test runs clockwise and
anticlockwise at 128 and 256 half-steps/second, showing direction, commanded
speed, completed steps, and observed software step rate in the terminal.

## Wiring

| Module input | Pi physical pin | BCM GPIO |
| --- | --- | --- |
| IN-A / IN1 | 32 | 12 |
| IN-B / IN2 | 35 | 19 |
| IN-C / IN3 | 38 | 20 |
| IN-D / IN4 | 40 | 21 |
| GND / minus | 34 | Ground |

Pin 34 is ground, not the module's positive supply. Connect the module's motor
supply to a supply rated for the motor's voltage and current, with a common
ground to pin 34. Do not power the motor from a GPIO or the Pi's 3.3 V rail.
For a bare ULN2003A, connect the emitter/GND to ground and the COM clamp-diode
connection to the positive motor supply; connect the unipolar motor's common
wire there too. Check the module labels and motor voltage before powering it.
The chip is a Darlington switching array, so the software generates the coil
sequence; it has no step/direction interface or speed feedback.
See the [TI ULN2003A datasheet](https://www.ti.com/lit/ds/symlink/uln2003a.pdf).

These GPIOs overlap the existing keypad wiring. Disconnect the keypad from
GPIO12/19/20/21 before connecting the motor. The board configuration disables
automatic startup of `keypad-display.service`; the motor driver holds its four
GPIOs even while idle. The standalone LCD uses different GPIOs and can still
be tested separately.

## Build and boot

```sh
./scripts/build-rpi4b.sh
```

The image installs `uln2003a` (which pulls in the versioned kernel module) and
`uln2003a-test`. Installing the `uln2003a` recipe package ensures BitBake pulls
the module into the image. The board configuration deploys
`overlays/uln2003a.dtbo` to the FAT boot partition and adds
`dtoverlay=uln2003a` to `config.txt`. Flash the new WIC image for initial setup.
Rootfs-only RAUC updates do not add or change overlays on the shared FAT boot
partition. For an existing SD card, build and install the bundle without an
automatic reboot:

```sh
./scripts/build-rpi4b.sh rpi4-update-bundle
./scripts/flash-ota-rpi4b.sh PI_ADDRESS
scp build/rpi4b/build/tmp/deploy/images/raspberrypi4-64/uln2003a.dtbo \
    root@PI_ADDRESS:/tmp/uln2003a.dtbo
ssh root@PI_ADDRESS
```

After the installation succeeds, verify `/boot` is mounted as FAT, back up the
current configuration, and install the overlay on the Pi:

```sh
findmnt /boot
cp -p /boot/config.txt /data/ota/config.txt.before-uln2003a
cp /tmp/uln2003a.dtbo /boot/overlays/uln2003a.dtbo
```

Add the following at the end of `/boot/config.txt`, unless the overlay is
already enabled. The `[all]` section makes the setting apply regardless of
preceding board-specific sections:

```text
[all]
dtoverlay=uln2003a
```

Disable the old keypad service, flush the boot partition, and reboot:

```sh
systemctl disable --now keypad-display.service
sync
reboot
```

Check the driver on the target:

```sh
modprobe uln2003a
dmesg | grep -i uln2003a
ls /sys/bus/platform/drivers/uln2003a/*/status
gpioinfo -c gpiochip0 | grep -E 'line +(12|19|20|21):'
```

The GPIOs should be owned by the motor driver. If probe reports `Device or
resource busy`, check for the keypad service or another GPIO consumer.

## Run the test

Run as root on the Pi:

```sh
uln2003a-test
uln2003a-test --direction cw --speed 128 --steps 512
uln2003a-test --direction acw --speed 128 256 400 --steps 1024
```

Each move releases the coils after its final phase interval. Ctrl-C, SIGTERM,
timeout, module removal, and normal shutdown also release them. A process
killed with SIGKILL cannot perform cleanup, but every accepted move has a
finite step count and the driver releases the coils when that count finishes.
No motor movement starts automatically at boot.

The harness defaults to 4096 nominal half-steps per shaft revolution, a common
approximation for geared 28BYJ-48 motors. Set `--steps-per-rev` for your motor.
The displayed RPM is calculated from that value and the requested speed.
The observed rate counts electrical phase updates; it does not measure shaft
motion. Verify both shaft directions visually and check for stalls. Linux
scheduling can slow the phase rate, and this driver provides no acceleration
ramp. Start with a low speed and increase it for your motor and load.

Clockwise depends on the motor's coil order and which end of the shaft you
observe. If the physical direction is reversed, use this boot configuration:

```text
dtoverlay=uln2003a,reverse
```

## Device-tree binding and control interface

This is a project-local binding, not an upstream Linux binding:

```dts
uln2003a {
    compatible = "jamesc,uln2003a-stepper";
    coil-gpios = <&gpio 12 0>, <&gpio 19 0>, <&gpio 20 0>, <&gpio 21 0>;
    /* reverse-direction; */
    status = "okay";
};
```

Exactly four `coil-gpios` are required, ordered IN-A through IN-D and active
high. Optional `reverse-direction` reverses the sequence. The provided overlay
accepts `in1`, `in2`, `in3`, `in4` BCM GPIO overrides. GPIO descriptor handling
uses the [Linux GPIO consumer interface](https://docs.kernel.org/driver-api/gpio/consumer.html).

Attributes under `/sys/bus/platform/devices/uln2003a/`:

| Attribute | Operation |
| --- | --- |
| `move` | Write `cw RATE COUNT` or `acw RATE COUNT`; RATE is 1–1000 half-steps/s and COUNT is 1–1000000 half-steps. |
| `status` | Read `running`, `direction`, `speed`, `completed`, and `remaining`. Speed is the requested rate; after stopping it retains the last request. |
| `stop` | Write `1` to cancel the current move and de-energize all coils immediately. |

A second move while running returns `EBUSY`. Invalid commands are rejected
before changing the motor state. The sysfs writes require root; reads allow
monitoring from another terminal. For example:

```sh
motor=/sys/bus/platform/devices/uln2003a
echo 'cw 128 512' > "$motor/move"
cat "$motor/status"
echo 1 > "$motor/stop"
```

Kernel compilation and host harness tests can verify software behavior;
electrical operation and shaft direction require the connected target.

```sh
python3 -m unittest discover -s tests -v
```

## Verified deployment on 2026-10-13

The new WIC image and signed RAUC bundle were built for `raspberrypi4-64`
with Linux `6.6.63-v8`. All three new recipes completed package QA, and all six
host harness tests passed: completion, busy-device rejection, interruption,
incomplete movement, timeout, and malformed status handling.

The bundle was installed on the Raspberry Pi 4 Model B Rev 1.2 at
`192.168.1.3`, switching from slot A to slot B. The shared boot overlay was
installed separately. The original boot configuration is backed up on that
device at `/data/ota/uln2003a-boot-backup.g2UCmD/config.txt`. The existing SSH
host keys were copied into the installed inactive rootfs before reboot, so
the Pi retained its verified SSH identity.

After reboot, checks confirmed:

- `/` mounted from `/dev/mmcblk0p3` and the command line contained `rauc.slot=B`.
- RAUC reported slot B booted, activated, and good; the mark-good service succeeded.
- `uln2003a` was loaded and the device-tree node bound to the driver.
- Status was `running=0 direction=clockwise speed=0 completed=0 remaining=0`.
- `uln2003a-test --help` ran successfully on the target.
- `keypad-display.service` was disabled.
- The installed harness, module, and overlay hashes matched the build artifacts.

No motor move was commanded during deployment verification. Shaft direction,
stall behavior, and actual motor speed still need a physical test. Start it
from the development host with:

```sh
ssh root@192.168.1.3 uln2003a-test
```
